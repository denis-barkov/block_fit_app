# BlockFit NYC operations

## Back up and restore

A portable JSON snapshot carries application and migration versions. A private snapshot includes business records, account password hashes, and compact AI spending totals. It omits sessions, provider credentials, and cached AI responses. Version 0.1.0 adds the saved-location preference and a timestamped removal history. Private snapshots include the history. Earlier supported snapshots restore saved locations with the preference enabled. Treat the file as private data. Store it under the ignored `.blockfit/` directory or outside the checkout and use encrypted storage for retention or transfer. AI cooldown state and caches are transient. Private restores preserve older accounting totals as historical data.

1. Stop or suspend user traffic and wait for in-flight writes before a private export. Locally, use `make suspend ENV=local`. Export with `make snapshot ENV=local SNAPSHOT=.blockfit/pilot-private.json`. Run `make resume ENV=local` if you want to reopen that source.
2. To share a clean demonstration dataset, run `make snapshot ENV=local MODE=demo SNAPSHOT=.blockfit/pilot-demo.json`. This builds the stock synthetic dataset in a temporary local database. It contains no accounts, sessions, private requests, or credentials carried over from the source.
3. Choose a directory that does not yet exist, for example `.blockfit/restore-qa`. Run `BLOCKFIT_STORE=.blockfit/restore-qa make restore ENV=local SNAPSHOT=.blockfit/pilot-demo.json`. The script migrates the fresh directory, imports the snapshot, checks record counts and foreign keys, and leaves the app suspended.
4. Use the same `BLOCKFIT_STORE` for subsequent commands. For a demo restore, create a fresh staff account with `make staff-create ENV=local` and self-register a resident after resume. Run `make resume ENV=local` then `make dev ENV=local` against that store. Verify inventory, role access, and the expected comparison. A private restore preserves the account password hashes and requires sign-in again.

For a Cloudflare restore, provision a separately named destination database before restoring. Keep the destination undeployed while importing, then deploy with a fresh `AUTH_SECRET` and chosen operator credentials. Resume when you have reviewed results. Keep the source and destination manifests and backups distinct. The `RETAIN` option in `make destroy ENV=prod` removes the Pages project and Worker while retaining D1. The `DELETE` option also removes the named D1 UUID.

## Upgrade an existing database to the equipment catalog

Migration `0006_equipment_catalog.sql` retains the IDs `pull-up`, `parallel`, and `sit-up` and adds foreign keys across all four category reference tables. The old schema only permitted those IDs. If the migration reports an unmapped value, stop and inspect distinct `category` values in `equipment`, `candidates`, `demand`, and `synthetic_demand` against the migration’s legacy mappings before proceeding. Private snapshots include catalog changes and proposal review history. Stock demo snapshots omit proposals and accounts. A pending proposal preserves its submitted pin even if the resident changes the saved pin later. Recorded requests still follow the existing move workflow. The current release preserves the submission confirmation time and has no automatic request expiry.

- **Local.** Use the running release’s `make suspend ENV=local` and `make snapshot ENV=local SNAPSHOT=.blockfit/before-catalog.json` before upgrading a populated store. Stop the old dev server. In 0.3.0, verify the backup in a fresh directory with `BLOCKFIT_STORE=.blockfit/catalog-restore-qa make restore ENV=local SNAPSHOT=.blockfit/before-catalog.json`. For the intended local store, run `make db-migrate ENV=local`, `make resume ENV=local`, and `make dev ENV=local`. Optionally run `make seed-proposals ENV=local` for illustrative review examples. Repeating it preserves prior review decisions.
- **Production, once authorized.** Use the deployed release’s tooling for `make suspend ENV=prod` and `make snapshot ENV=prod SNAPSHOT=.blockfit/prod-before-catalog.json` after in-flight writes drain. Restore and verify that snapshot locally with the 0.3.0 tooling. Verify the intended target with `make deploy ENV=prod DRY_RUN=yes`. While traffic is suspended, run `make db-migrate ENV=prod`, then `make deploy ENV=prod`. Resume with `make resume ENV=prod` and verify with `make smoke-prod ENV=prod`. Keep the pre-upgrade snapshot private. [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/)

## Upgrade or restore the goal schema

Migration `0007_program_goals.sql` adds nullable candidate schedule estimates and shared goals. Existing schedules start blank. A private 0.4.0 snapshot preserves goals, deletion markers, schedules, and spend. The restore workflow accepts 0.3.0 snapshots and supplies blank schedules. AI results and staff in-flight or cooldown records are transient. Verify the upgrade with `make db-migrate ENV=local` on a private disposable copy and test restore with `BLOCKFIT_STORE=.blockfit/goal-restore-qa make restore ENV=local SNAPSHOT=.blockfit/before-goals.json`.

## Production rollout

1. Set the intended account and project in `.env.prod`. Reuse Wrangler OAuth for deployments and supply the account-scoped Resource Tagging token. Keep the auth secret and OpenAI key in the protected environment. Enable AI with `AI_ENABLED=true`. The recovery contact is optional.
2. Run `make release ENV=prod DRY_RUN=yes` from the release checkout. This checks the configured Cloudflare target and packages both artifacts without modifying Cloudflare or calling OpenAI. The initial package uses a provisional origin until Pages assigns its hostname.
3. For the first presentation deployment, run `make release ENV=prod DEMO=yes ACCOUNTS=default` from a clean commit and an interactive terminal. The command verifies types, test suites and packaging, reconciles project resources and tags, applies migrations, adds the approved synthetic dataset and goals, and applies the named account plan. Presentation passwords are entered at the hidden prompt and dedicated test accounts read protected credentials. Existing passwords, edits and goal deletions are preserved. Proposal presets remain local.
4. The release uploads secrets with the private Worker and publishes Pages after checking the Worker binding and private routing. It records the commit, both deployed versions, migration level, origin, AI settings, and smoke outcome in the ignored deployment manifest. If the first smoke run fails, the release suspends application access for diagnosis. A failure identifies the phase and may leave earlier steps complete. Repeat the release after resolving the issue, or use the individual Make targets to finish a verified partial deployment.

For later releases, omit `DEMO` and `ACCOUNTS` to preserve the current data and accounts. If migrations are pending on a previously migrated database, first use `make suspend ENV=prod` and let writes drain. The release saves a private SQL backup of the old schema before applying migrations. For portable JSON, use `make snapshot` with the running release's code. After reviewing the migration, run `make resume ENV=prod` and `make smoke-prod ENV=prod` to record the live result.

Suspension blocks application operations and AI. Requests can still reach Pages and the Worker, and static assets remain available. The workflow uses Pages, a Worker, D1 and native warning and error logging on the existing account. It does not configure subscriptions or paid add-ons. Account quotas are shared. Check Workers CPU and invocations, D1 rows and storage, and account billing before increasing traffic. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) · [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)

## Rebuild in another Cloudflare account

Use a separate checkout of the release and run `make setup` to prepare the ignored configuration templates and install dependencies. Set a new `CLOUDFLARE_ACCOUNT_ID`, the new account's scoped token, a unique `PAGES_PROJECT_NAME`, and a fresh `AUTH_SECRET` in `.env.prod`. Run Wrangler login for the new account if needed. Clear `APP_ORIGIN` to discover the new Pages URL. Set `DEPLOYMENT_SUFFIX` to distinguish a parallel installation in the same account. Root `.env` supplies shared resource and tag values, including the project name and funding. Keep each account's protected manifest and credentials separate.

- **Fresh presentation.** Check `make release ENV=prod DRY_RUN=yes`, copy the approved account definitions and set fresh protected smoke credentials, then run `make release ENV=prod DEMO=yes ACCOUNTS=default`.
- **Restore data.** Use `make provision ENV=prod` for a fresh, undeployed target in the new account. Import the protected JSON with `make restore ENV=prod SNAPSHOT=/private/path/to/snapshot.json`. Run `make release ENV=prod` with no initialization flags to preserve imported records. A private restore retains password hashes and requires sign-in again. Restore the corresponding smoke credentials separately, or securely create/reset those dedicated accounts before smoking. Inspect the restored data and authorize reopening with `make resume ENV=prod`, then run `make smoke-prod ENV=prod`.

## Recover deployed code

First suspend and drain the target. Choose the explicit Pages and Worker identifiers for a pair marked verified in the protected deployment manifest, then run `make recover ENV=prod PAGES_DEPLOYMENT=… WORKER_VERSION=…`. Recovery checks both IDs against that project and requires the exact applied migration level. It sets the Worker version before switching Pages and leaves the application suspended. Review the result, then use resume and smoke. If the Pages step fails, keep the app suspended and resolve that step or publish corrective code. On the first release there may be no earlier verified pair. Database recovery is a separate restore into a fresh target. [Pages rollbacks](https://developers.cloudflare.com/pages/configuration/rollbacks/) · [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)

## Production smoke test

Define one resident and one staff login with purpose `automated-test` in the target account definition. Use `.blockfit/local-smoke.env` or `.blockfit/prod-smoke.env` with mode 0600 for the protected test credentials. Set `RESIDENT_EMAIL`, `RESIDENT_PASSWORD`, `STAFF_EMAIL`, and `STAFF_PASSWORD` privately. Use unique credentials for production and keep the operator account-definition JSON free of passwords.

Run `make accounts-provision ENV=prod` to preview the named changes. Once authorized, use `APPLY=yes` and confirm the deployment name. Presentation credentials are prompted separately. Existing passwords stay in effect on a repeat run. Use the separate recovery or session-revocation command for intentional changes.

`make smoke-prod ENV=prod` checks canonical routing, static assets, the response policy, cross-origin rejection, and unauthenticated API access. It signs in through the ordinary API with the two dedicated accounts, checks the isolated staff comparison, cleans up its scoped request and temporary location, and signs out. No AI call runs in this command.

Before sharing the URL, check public search, map and directions, resident registration and password changes with a disposable account, and authorized staff catalog and planning journeys. Check actual Worker CPU and errors for auth, planning, and proxy requests. If telemetry is unavailable, record that gap. For live AI, use one small synthetic comparison that fits a single evaluation batch, run one goal evaluation and one staff Explain, and request one resident suggestion. Repeat the same inputs to verify cache reuse. Allow at most one uncached generation per feature and four in total if testing both resident stages. Stop after a provider error and use mocked tests for further diagnosis.

## OpenAI project settings

Migration `0008_ai_cooldowns.sql` stops application-side spending and daily attempt accounting for new requests. Apply it with `make db-migrate ENV=local` to update an existing local store. The Worker uses the configured OpenAI project key and enforces a five-second cooldown per account and coalesces duplicate work. Enable AI with `AI_ENABLED=true`. Manage the monthly spend limit and model access in the OpenAI project. Enable **Enforce a hard limit** to stop API traffic after tracked spend reaches the limit. Enforcement can lag. [OpenAI project settings](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform)
