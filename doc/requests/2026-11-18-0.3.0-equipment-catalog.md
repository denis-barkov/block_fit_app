**Target commit:** `0.3.0v - Add equipment catalog and resident type review`

### Included

- Signed-in resident submission of a requested type that is missing from the catalog.
- Staff approval under the submitted or corrected name, matching to an existing active type, and rejection with a short reason.

## 2. Domain rules and single source of truth

An **equipment type** is a category such as “Pull-up bars.” An **equipment record** is a particular installed item or site entry. A **candidate site** is a proposed investment location. Creating or approving a type does not create installed equipment, approve construction, establish feasibility, or promise funding.

The database catalog becomes the single source of available types and their display names. Reference types through immutable IDs. A rename is a label correction, not a new category; it must propagate throughout the application without changing references or rewriting request histories. Do not let staff repurpose an existing type into a materially different category through renaming; explain that a new category should be created instead.

Retain only necessary fields: stable ID, canonical name, normalized uniqueness key, optional description, active status, created/updated timestamps, and lightweight concurrency metadata where required. Reuse existing entities/columns if they already satisfy this contract. Enforce case/whitespace-normalized uniqueness across active and inactive types, not merely in frontend validation. Preserve sensible spelling/capitalization in display names. Do not use fuzzy matching to automatically merge distinct categories.

Mutable catalog entries belong in the database. Behavioral defaults and limits belong in shared `config/`; visual tokens belong in `design/`. Do not keep a second authoritative list in config, frontend unions, prompts, seeds, or API validators. Seed definitions initialize data; they must not overwrite staff edits whenever the app starts or a seed is rerun.

Generic new types must work without a code release. Where old code has category-specific radii, icons, or presentation mappings, retain existing behavior for migrated types and supply an explicit shared generic default for new types. Unknown costs remain unknown; do not fabricate installation prices or maintenance assumptions from a new category name. If a feature genuinely needs type-specific information, show a clear missing-information state rather than crash, substitute another type, or invent facts.

## 3. Staff catalog interface

Add **Equipment types** to the existing staff navigation/layout using its established styling. One page with **Types** and **Proposals** tabs or equivalent compact sections is sufficient. Reuse existing list, form, dialog, status, icon, and info-hint components. No new icon library or independent design system.

The catalog list shows name, active/inactive status, and compact actions. Search by name and filter active/inactive/all. Creating a type requires a name; description is optional. Renaming and description edits preserve its ID. Show existing matches when creating/renaming, and return a useful conflict message if another staff member creates the same name concurrently.

Before deactivation, show that the type will stop accepting new selections and that linked records remain. Never hard-delete a referenced type. Provide reactivation on the same record rather than recreating a duplicate. Do not implement a delete action in this release.

Reuse the installed icon set for actions, with concise text on primary actions. Icon-only controls require accessible names. Reuse clickable info hints for secondary explanations; make them keyboard/touch accessible with focus and Escape behavior consistent with existing components. Do not hide required validation, review status, rejection reasons, or consequential confirmation text exclusively behind an info icon. Keep the page usable on mobile/tablet without a wide unresponsive table.

## 4. Resident submission workflow

Keep normal requests for existing active types unchanged. In the signed-in request form, add **“Suggest another type”** as a distinct action, not a fake equipment-type option stored as a category.

The resident enters a proposed name and optional short description. Reuse the existing request-location and optional suggested-site workflow; do not force the resident to repeat information already provided. A request location is still required under the normal request rules. A suggested installation site remains a separate optional field, not a replacement for the resident's demand location.

Before submission, show matching existing active catalog names and a way to select one. This is a suggestion, not an automatic semantic match. Do not expose other residents' proposals, notes, identities, or private locations through search. If staff has deactivated an exact normalized name, do not create another active type or offer it as an ordinary request; explain that it is currently unavailable. Do not reveal private staff notes.

Submit the type proposal and associated request intent as one consistent operation. The UI must not claim that an ordinary active request exists yet. Show it in the resident's own requests list as **“Awaiting type review”**, with its submitted name and a short explanation that it is not counted in planning until approved.

Allow withdrawal of a pending intent. For this MVP, a resident corrects a pending proposal by withdrawing it and submitting the corrected version; do not build versioned proposal editing. A withdrawn intent must never activate later, even if staff approves the same type for another resident.

After approval, show the canonical type name and link to the resulting ordinary request, or to an already active matching request if duplication was prevented. Retain the original submitted name privately for review context. After rejection, show the short reason and allow a corrected new submission subject to limits. No emails or push notifications; in-app state is sufficient.

## 5. Review decisions and request activation

The staff proposal queue shows proposed name, optional description, submission date, status, and suggested catalog matches. Reveal personal/request-location details only through existing authorized staff workflows when necessary; type review does not require displaying private coordinates in the queue.

Review actions:

| Action | Result |
| --- | --- |
| Approve as new type | Create one active canonical type and resolve the proposal to its ID. |
| Correct name and approve | Same, using the staff-approved spelling/name; retain original text privately. |
| Use existing type | Resolve to a selected active catalog ID without duplicating it. |
| Reject | Require a short reason; do not create a type or active request. |

Show the effect before confirming. If the chosen name now exists, direct staff to use that record instead of creating a near-duplicate. Never silently reactivate an inactive type; staff must deliberately reactivate it through catalog management first.

Approval must use an atomic database operation or supported transaction/batch pattern so catalog creation, proposal resolution, and associated request handling cannot partially succeed. Do not emulate a transaction with unrelated unprotected writes. Use conditional state/version checks to prevent two staff reviewers from making conflicting decisions. Repeated network submissions must be idempotent. Return the already completed result or a clear stale-review conflict, never duplicate records.

### Request ownership and uniqueness

- Reuse normal request creation rules and the existing one-active-request-per-resident-per-type invariant. Enforce it server-side with database protection or an equally race-safe existing mechanism.
- If approval finds an existing active request for the same resident and canonical type, keep that request unchanged. Mark the proposal resolved to it and explain “You already have an active request for this type.” Do not count twice or overwrite the existing pin, note, or confirmation date.
- If a prior withdrawn request exists, reuse the current normal restore/create semantics, but do not silently overwrite unrelated data. A new submitted pending intent represents a new explicit request; the withdrawn old request alone does not.
- Preserve actual resident submission/confirmation timestamps. Staff approval is a separate timestamp and must not masquerade as a recent resident reconfirmation. If existing freshness rules make the intent stale before approval, require resident reconfirmation before counting it.
- Withdrawal/deletion of the intent or account before approval prevents activation. Resolve races safely. Preserve only the history permitted by existing deletion/privacy rules.
- Separate proposals from different residents may resolve to the same canonical type, but each resident's intent and status remain separate. Review them individually in this version; do not add bulk semantic grouping or silently approve other proposals.

Maintain minimal review metadata: status, reviewer ID, decision time, final type ID where applicable, reason, and resulting request reference/outcome. This is application state needed to understand decisions, not a new verbose logging system. User text must not be dumped into operational logs.

## 6. Deactivation behavior

Define and implement this consistently:

- Inactive types cannot be selected for new requests, equipment records, candidate sites, or proposal resolution. Stale forms are rejected server-side with a useful message.
- Existing equipment, candidates, and resident requests retain their references and remain inspectable. Do not delete or silently withdraw them. Staff can edit unrelated fields on those records without being forced to reclassify them.
- Active public selectors omit inactive types. Existing publicly visible equipment can still display its category label in an all-equipment view or detail page; deactivating a category must not falsely imply that an installed item disappeared or is unsafe. Do not newly recommend an inactive category through AI helpers.
- Existing requests show “Type currently unavailable” where appropriate and remain withdrawable. Reconfirmation/new demand for inactive types is disabled. Normal planning excludes inactive categories, with a clear state for old selections/saved scenarios; historical records remain accessible.
- Reactivation restores availability under the same ID. It does not reset age, reconfirm withdrawn requests, or bypass normal eligibility/freshness rules.

Do not confuse category inactivity with equipment condition, site feasibility, public access, or verification. Those remain separate facts.

## 8. Validation, privacy, and configuration

Server-side authorization on every catalog mutation and review endpoint is required. All staff are equal within the existing staff role; no new role levels. Residents can submit/read/withdraw only their own proposals and intents. Anonymous users can read active catalog information but cannot submit proposals. Preserve existing session, CSRF/origin, and API validation protections.

Initial limits, stored once in the existing configuration structure and shared safely with UI validation:

| Parameter | Default |
| --- | --- |
| Type/proposal name | 2–80 trimmed characters |
| Optional description | Up to 500 characters |
| Rejection reason | 1–240 trimmed characters |
| Pending proposals per resident | 5 |
| New proposals per resident per UTC day | 10 |

Use stricter compatible existing limits if present and document the choice. Daily submission limits include proposals later withdrawn or rejected. Retries of the same idempotent submission do not count twice. Block a duplicate pending normalized name from the same resident; point to their existing pending item. Reuse existing general rate-limit and transaction mechanisms. No CAPTCHA/email flow or new paid service is required.

Reject empty/invalid names, control characters, invalid IDs, excessive payloads, and unsupported state transitions. Preserve normal Unicode names; do not use an English-only character whitelist. Render all submitted names/descriptions/reasons as text through existing safe components, including exports and map popups. Treat those strings as untrusted data if later included in AI context.

The client cannot set approval status, canonical type ID on an unapproved proposal, reviewer identity, timestamps, account owner, synthetic/test classification, or quota values. Never return private request pins or proposal text from public catalog endpoints. Keep personal notes out of logs and test fixtures.
