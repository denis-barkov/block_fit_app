> **AI prompt files and substitution**
>
> When an application sends prewritten instructions to an AI API, keep the instruction text in dedicated, version-controlled plain-text files under `prompts/`, grouped by purpose where useful. This includes system/developer instructions, task templates, and any retry or repair instructions. Do not scatter or duplicate prompt prose in source code. Use one maintained loading/rendering mechanism appropriate to the application runtime.
>

Require all referenced keys, reject unsupported keys, replace every occurrence in a single pass, and never recursively interpret inserted values. Prompts without placeholders remain plain text and require no artificial variables. Keep stable instructions separate from untrusted input, preferably passing structured input in a separate data message. Do not inject secrets or unnecessary personal data.
>
> Keep prompt files as the single source of instruction text, include them in the actual build/runtime artifact, and test loading and substitution. Include the effective prompt content/version in AI cache invalidation. Keep project-specific prompt organization, schemas, and configuration documented in README or focused documentation rather than this reusable rule.

Apply this convention immediately in the same change. A `.txt` file is the default prompt format, not a TypeScript string disguised as a prompt file.

## 3. Prompt implementation

### File ownership and loading

- Place the investment instructions under `prompts/investment-comparison/`, with separate `.txt` files for different message roles only where that matches the existing API integration. For example, `instructions.txt` and `task.txt`; avoid splitting a short prompt into many fragments.
- Move all existing instruction prose for this feature out of API handlers and other source files, including any fallback/repair instructions that are actually used. Keep schemas, request construction, validation, and calculations in code.
- Use build-time raw-text inclusion or an equivalent supported bundling mechanism for the existing Worker runtime. Do not rely on a development-machine filesystem or runtime filesystem reads unavailable in deployment. Keep server instructions out of the browser bundle.
- No dynamic user-provided file paths or filenames. Resolve prompts through fixed, code-owned identifiers.
- Preserve message roles supported by the current integration. The instruction text belongs in the appropriate trusted instruction message; scenario data belongs in a clearly identified data message. Do not concatenate resident text into authoritative instructions.

### Minimal placeholder contract

Use a small shared renderer with named tokens, for example `{{output_word_limit}}`. Values may come from configuration constants or runtime logic. Define permitted keys for each template and accept strings and finite numbers; serialize structured data explicitly rather than relying on implicit object conversion.

1. Validate template syntax and its required keys before an API request.
2. Reject missing, unknown, malformed, or inappropriate values with a controlled local error; make no API call and do not consume a spending reservation for a request that was never sent.
3. Replace all matching tokens using literal, single-pass substitution. Values containing `$`, braces, quotes, or newlines must not activate replacement syntax, code, or nested placeholders.
4. A value containing text such as `{{another_key}}` remains literal data. Do not scan substituted data as if it were part of the original template.
5. A template with no tokens loads unchanged with no variables required.
6. Never support shell interpolation, `eval`, JavaScript expressions, arbitrary includes, or a general templating language.

Prefer structured JSON scenario input in a separate message over injecting the entire scenario into the instructions. Placeholder substitution is a maintenance feature, not a defense against prompt injection: keep free-text input constrained and untrusted even after rendering.

## 4. Improve the input contract before changing the wording

Trace the current meaning of `coverage`, `unmet`, and `perRequester`. The observed explanation said it could not relate option coverage to unmet demand. Fix missing definitions in the AI payload; do not paper over ambiguous or incorrect calculations with nicer prose.

Send a bounded, validated snapshot containing:

| Field group | Required meaning |
| --- | --- |
| Scenario | Equipment category, analysis area, configured radius and its straight-line approximation, comparison horizon, and synthetic/real data designation. |
| Demand | Eligible unique active requesters, already served requesters, and baseline unmet requesters; use the existing eligibility definitions. Requests are observed demand, not total population need. |
| Options | Stable internal ID plus readable site/option name; single site or combination; constituent site IDs for combinations. |
| Coverage | Unique previously unserved requesters newly covered for the selected category; combinations use the union, not the sum. Label any other coverage measure separately. |
| Costs | Currency `USD`, explicit internal unit, low/base/high upfront and lifecycle costs, horizon, included components, missing components, and the existing assumptions. |
| Budget fit | Explicit low/base/high fit against the upfront budget; never compare lifecycle totals to that budget unless the application explicitly defines a separate lifecycle budget. |
| Eligibility | Comparison eligibility and exclusion reasons; feasibility status; sufficient-data status; distinguish these from any official authorization. |
| Ranking | Code-computed highlighted option, exact selection rule, ties, and limitations. Use the current established rule; do not invent a second ranking in the prompt. |

Keep private addresses, resident identities, account details, and raw individual request records out of the AI payload. Aggregate numbers and candidate labels are sufficient.

Retain integer minor units internally if already used. Supply deterministic display strings such as `$20,000` alongside machine values where useful; do not rely on the model to convert currencies or recalculate ratios. Supply a reason for an unavailable metric: zero additional coverage differs from missing cost data. Unknown maintenance is not zero maintenance.

If this inspection discovers an actual calculation defect, fix a narrowly related defect with regression tests and disclose it in the handoff. Do not redesign the economic model or silently change the ranking formula. If the metric cannot be established safely, suppress the recommendation and display a clear explanation of what is missing.

## 5. Explanation behavior and presentation

Keep the existing UI structure where it works. Use approximately 120–180 words for an ordinary comparison, with a configurable upper target around 220 words. Do not force four sections when there is nothing useful to put in them.

The explanation should contain:

1. **Leading finding:** name the code-selected strongest eligible option and explain the specific advantage. Qualify it as strongest on the selected metric, not the universally best investment. If there is no eligible option or there is a tie, say so.
2. **Meaningful tradeoffs:** describe coverage/cost differences that change the decision, combination overlap, budget uncertainty, and material alternatives. Avoid restating every row or every low/base/high value.
3. **Checks before proceeding:** identify missing costs, unreviewed feasibility, or important scenario limitations. Give a practical next check without implying official approval.

Use site names rather than bare IDs, readable USD amounts rather than cents, and plain-language metrics. Say “15 additional requesters served” only when the data contract confirms that interpretation. For zero new coverage, say “No additional demand served; cost per additional requester is not applicable,” not `null` or “data unavailable.”

For the previously observed scenario, the desired reasoning is: the first eligible option is cheaper than the second while serving the same additional demand; a zero-benefit option does not improve access; an option with unknown maintenance cannot be fully compared; a combination adding no unique coverage at higher cost offers no coverage advantage. These are test expectations for a fixture, not hardcoded facts about real sites.

Do not assert savings, ROI, community-wide benefit, fairness, actual walk times, land availability, construction suitability, or government approval from the supplied comparison alone. Do not say “no other data is missing” merely because the model sees no missing-field flags; say “No other missing fields are flagged in this comparison” when relevant. Explain substantive limitations rather than technical JSON details.

Any AI finding must agree with the deterministic comparison. Missing inputs, untrusted text, or a model error must never change the table, eligibility, selected sites, or ranking. The comparison remains fully useful without AI.

## 6. Validation, caching, and operating limits

- Treat invalid output as a controlled failure. Keep the comparison visible and offer the existing manual retry behavior, subject to limits. No new automatic paid repair/retry loops.
- Build cache keys from a stable serialization/hash of all relevant comparison inputs, effective prompt contents (including rendered instruction values), output-schema version, configured model, and material generation settings. Do not use raw personal data in keys or logs.
- A prompt, model, schema, or relevant scenario change invalidates the previous explanation; unchanged requests reuse a valid result. Never show an old scenario explanation as current while regeneration is pending.
- Preserve existing staff authorization, usage reservations, spending limits, daily limits, concurrency controls, and minimal logging. Prompt changes must not reset usage accounting. Do not log rendered prompts, payloads, credentials, or full responses merely to debug this feature.
- The browser must not make OpenAI requests directly or receive API credentials. Public browsing and ordinary comparison calculation must not trigger AI requests.
