BlockFit NYC · NYCEDC project concept · Resident state

Design notes · signed-in state

  1. Same public application: Explore equipment returns to the public map without losing session requests. My requests returns here. No separate resident analytics dashboard.
  2. One saved location: choose one synthetic point for this demo. Changing it moves all active requests to that point after explicit confirmation. Withdrawn requests retain their previous location until restored. Real address verification, household members and work/school locations are deferred.
  3. Demand integrity: one active record per resident and equipment category. Editing or reconfirming updates the existing record; it never creates another vote. Withdrawing removes it from active demand, and restoring reuses it.
  4. Two-step form: review equipment, location, note and optional site suggestion before recording. Suggested sites never replace the demand origin or become approved candidates automatically.
  5. Staff connection: in the working MVP, recorded/updated/withdrawn requests change the planning dataset. This standalone file demonstrates state transitions only; it is not connected to the City workspace file.
  6. Lifecycle: only Recorded and Withdrawn exist here. Do not imply agency review, construction or funding. Show last-confirmed dates; automatic expiry/decay is deferred.
  7. Prototype boundary: simulated authentication, in-memory records, fixed sample points and no external calls. Reload resets the demo. Shared production authentication and server enforcement belong to implementation.

Resident wireframe · 17 November 2026
Official park maintenance reporting ↗

Design notes · public entry point

  1. Open browsing: map, list, equipment details, verification information and official reporting links never require sign-in. No separate marketing landing page.
  2. Location search: this wireframe uses two synthetic areas. The working MVP needs a geographic area selector or map pin; address search is added only if a suitable service is available. Do not force account creation or browser-location permission.
  3. Verification is specific: each equipment item has its own status. A verified park does not imply every item is verified. Unknown opening hours and accessibility remain explicitly unknown.
  4. Resident handoff: request buttons preserve selected equipment and search area. Sign-in appears only when starting a personal request. The next wireframe defines saved location, request submission and history.
  5. Responsive: desktop pairs the list with map/details; mobile stacks them. List-only view provides a usable alternative to map interaction. No full-screen map traps.
  6. Scope: no workout generation, photos, crowdsourced corrections or repair-management queue. Public demand overlays wait until aggregation and privacy rules are defined.
  7. Prototype limits: everything runs locally; no accounts, location collection, database, AI or live map service. Reload resets choices. All records and verification dates are illustrative.
